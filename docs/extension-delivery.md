# 扩展交付与更新机制（内置 / 在线 / 迁移）

> 本文说明：**套壳内置的 ST 扩展（card-compat、plot-pilot）是怎么送到用户机器上的**，以及 ST 本体更新 / 换机 / 重装 / 手动改过之后会发生什么。

## 一、两条通道

| 通道 | 来源 | 触发 | 适用 |
|---|---|---|---|
| **本地内置** | 安装包 `app.asar` 里的 `extensions/` | 套壳启动后 1.5 秒自动部署；托盘「部署/更新内置扩展」；工具箱「🧩 ST 扩展与插件 → 部署/更新内置扩展」 | 首次安装、离线、目标被删 |
| **在线更新** | GitHub `extensions/index.json` + 各扩展文件（raw.githubusercontent 优先，jsDelivr 兜底） | 启动后 6 秒自动检查（可关）；工具箱「检查扩展在线更新」 | 老套壳也能拿到新扩展，**不必重新发安装包** |

两条通道都写到同一个位置：`<dataRoot>/default-user/extensions/<扩展名>/`。目标目录唯一，所以**不会出现两份**。

## 二、部署规则（`lib/ext-deploy.js` / `lib/ext-remote.js`）

1. 目标不存在 → **安装**
2. 内置/在线的版本 > 目标 `manifest.version` → **更新**
3. 版本相同或目标更新 → **跳过**（不降级；用户手改过的同版本扩展不会被覆盖）
4. 目标目录没有 `manifest.json` → **不碰**，只报告
5. 覆盖时**不做镜像同步**：只写自带的文件，不删用户自己的文件
6. 每次部署写 `.shell-deployed.json`（版本 + 内容 sha1 + 时间 + 来源）留痕
7. 在线通道：先下齐该扩展**全部文件**并逐个校验 sha1，**全通过才写盘**；某个源内容陈旧就自动换下一个源

想强制覆盖（允许降级）：工具箱 🧩 组填 `tag`/`commit` → 「按指定版本应用」（内部走 `rollbackTo(ref)`，带 `force`）。

## 三、常见场景会发生什么

| 场景 | 结果 |
|---|---|
| **ST 本体更新**（`git pull` / 换版本 / 重装 ST 到新目录） | 扩展在 `Data/default-user/extensions/` 下，**ST 本体更新不动 Data** → 扩展保留 ✓；即使 Data 被清空，套壳下次启动会自动重新部署 ✓ |
| **套壳更新**（自动更新到新版） | 新安装包里的 `extensions/` 与 `index.json` 覆盖 `app.asar`；启动后按上面的规则比对，只会"补齐/升级"，不会把手改过的同版本覆盖 ✓ |
| **换机器 / 迁移 Data** | 把 `Data/` 一起带走 → 扩展跟着走 ✓；只带套壳不带 Data → 启动自动部署 ✓ |
| **删掉某个扩展目录** | 套壳下次启动「目标不存在 → 安装」自动装回 ✓ |
| **手动改过扩展（版本号没改）** | 保持你的改动（跳过）✓；想回到官方版 → 用「按指定版本应用」或删掉目录后重启 |
| **别人装套壳** | 安装 **v1.36.0 及以上**的安装包即自带两个扩展并自动部署；≤1.35.x 的老包没有，需要升级套壳或手动 `node scripts/ext-install.mjs` |
| **离线环境** | 本地内置通道可用（不需要网络）✓；在线更新会失败但只写终端日志，不影响使用 |

## 四、维护者发扩展的流程（版本解耦）

```
1. 改 extensions/<名字>/ 里的文件，并同步提升 manifest.json 的 version（改了就要升，否则两边都跳过）
2. node scripts/ext-index.mjs            # 重建 extensions/index.json（CI 会 --check，构建前也会自动跑）
3. git commit && git push                  # 推 main 即生效：老套壳启动就会比对到新版本
4.（可选）git tag vX.Y.Z && push           # 只有套壳本体也要更新时才需要发版
```

## 五、故障排查

| 现象 | 先看什么 |
|---|---|
| ST 扩展列表里没有这两个扩展 | 套壳是否 ≥1.36.0；`<dataRoot>/default-user/extensions/` 下是否存在目录；托盘「部署/更新内置扩展」的终端输出 |
| 有目录但版本旧 | 工具箱「检查扩展在线更新」；终端里 `[ext] … 跳过：` 的原因（已是最新 / 目标版本更新 / 无 manifest） |
| 在线检查失败 | 终端会打印试过的两个源与错误；国内网络可先开代理，或改用「按指定版本应用」并填一个可用 tag |
| 改了扩展没生效 | 确认 `manifest.version` 提升了、`index.json` 已重建、ST 页面已刷新 |

## 六、已知缺口（下一步要补的）

1. **没有可视化扩展管理器**：现在只有三个按钮（部署 / 在线检查 / 按版本应用）。计划在工具箱做正式面板：扩展列表（版本、来源、部署时间、是否有本地改动）+ 一键更新 / 回滚 / 重置 / 卸载。
2. **没有"本地改动"的可靠检测**：判断依据目前是版本号相等即跳过；计划把 `.shell-deployed.json` 里的内容 sha1 与磁盘现状比对，明确区分"未改动 / 已改动 / 缺失文件"。
3. **没有残留文件清理**：扩展改名/删文件时旧文件会留在目标目录（例如历史上 `vendor/` → `assets/` 的改名）。计划在部署记录里保存文件清单，升级时清理"上次有、这次没有"的文件。
4. **在线源单一**：只依赖 GitHub（raw + jsDelivr），且 jsDelivr 有 12 小时缓存。计划增加可配置的镜像/自建源，以及"离线包导入（zip/文件夹拖入）"。
5. **第三方扩展**：目前只认内置清单。计划支持用户添加"扩展源"（一个 index.json URL），并对每个扩展做 sha1 校验；不做签名的话至少要显示来源与哈希。
